Single Table Design

Una sola tabla DynamoDB con PK/SK polimórfico. Cada tipo de ítem comparte la tabla pero se identifica por su patrón de claves. Sin Scan, sin JOIN: un solo Query trae todo lo que necesitas.

¿Por qué es Single Table?

Todos los ítems de un reporte (META, EVT#, CONF#, MEDIA#) comparten la misma partición PK=REP#<id>. Un solo Query sobre esa PK trae el reporte completo: metadatos, historial, confirmaciones y medios adjuntos. Cero "JOIN", cero "Scan".

Patrones de Caché

Cinco patrones de caché diferentes, cada uno elegido por el caso de uso específico.

📖 Cache-Aside (Lazy Loading)

Dónde: detalle de reporte (rep:pub:{id}), catálogo (cfg:categorias), noticias.
Cómo: GET → ¿está en Redis? → Sí: devolver (CACHE HIT). No: Query DynamoDB → guardar en Redis con TTL → devolver (CACHE MISS).
Por qué: Los datos de lectura cambian poco. Solo se cachean los que se piden.

✍️ Write-Through

Dónde: crear reporte → feed, GEO, ranking, proyección pública. Confirmar video → media:videos.
Cómo: POST → escribir en DynamoDB → escribir en Redis (pipeline: 7 comandos en una ida). El reporte aparece de inmediato en el feed.
Por qué: Los datos nuevos deben ser visibles al instante.

🗑️ Invalidación

Dónde: cambiar estado (resuelto), confirmar reporte, publicar noticia.
Cómo: Borrar rep:pub:{id} y rep:full:{id}. La próxima lectura los reconstruye (Cache-Aside).
Por qué: Evita carreras: actualizar una caché que otro proceso también actualiza produce datos inconsistentes.

🚦 Rate Limiting

Dónde: crear reporte (5/hora por usuario), lecturas públicas (120/min por IP).
Cómo: INCR + EXPIRE (nx=True) en un pipeline. Si Redis cae, se deja pasar (fail-open).
Por qué: Protege contra abuso sin bloquear a usuarios legítimos si Redis falla.

⏰ Limpieza Perezosa (Lazy Expiry)

Dónde: feed y GEO (reportes con vigencia limitada).
Cómo: Sorted Set expira:activos con score = fin de vigencia. En cada lectura del feed: ZRANGEBYSCORE → retirar los vencidos.
Por qué: Los miembros de un Sorted Set no expiran solos (no tienen TTL individual).

Modo Degradado — Redis Caído

Si Redis no responde, NINGUNA operación falla. La Lambda continúa solo con DynamoDB (más lento, pero funcional).

¿Qué pasa cuando Redis cae?

📋

Feed (AP1)

Normalmente: ZREVRANGE feed:ciudad + MGET.
Degradado: Query GSI4 FEED#<fecha> de hoy y ayer, filtrar activos. Respuesta incluye "_fuente": "dynamodb".

📍

Cercanía (AP2)

Normalmente: GEOSEARCH geo:activos.
Degradado: Lee todos los activos desde GSI4, calcula Haversine en Python, ordena por distancia.

📄

Detalle (AP3)

Normalmente: Cache-Aside con rep:pub:{id}.
Degradado: Query directo a DynamoDB PK=REP#<id>. Siempre funciona.

✍️

Crear reporte (AP9)

DynamoDB se escribe siempre. El Write-Through a Redis falla silenciosamente (logger.warning). El reporte existe pero no aparece en el feed hasta que Redis vuelva.

🚦

Rate Limiting (AP18)

Si Redis cae, excede_limite() devuelve False (fail-open). No se bloquea a nadie.

🎬

Videos (AP23)

Normalmente: ZREVRANGE media:videos.
Degradado: Query GSI4 MEDIA#<fecha> de los últimos 7 días.
